🧪 Adalore Take-Home Challenge (2–3 hours max)
“Design the core of a post-purchase offer engine.”
This exercise is intentionally scoped to test architecture, reasoning, and communication, not UI polish.
🎯 Goal
Build a minimal backend that returns which offer should be shown on a Shopify Thank-You page, based on simple offer and merchant data.
It should feel like a tiny version of Adalore’s matching engine.

📌 Part 1 — Data Model (Core)
Design the data schema for these entities:
Merchant (a Host)


Offer (from an Advertiser)


Impressions / Clicks / Sales (tracking data)


Payout / Commission logic


Deliverable:
A simple schema (SQL or NoSQL) with fields and types.
One paragraph explaining why you chose this structure.
 Which indexes you’d add and which queries you expect to run most often.
One example of how you’d evolve the schema in v2 (e.g., adding budget caps) without major downtime.

📌 Part 2 — Matching Engine Endpoint
Create a single API endpoint:
GET /offer/next?merchantId=123&orderValue=60

It should return one offer that this merchant should show.
Use these simplified rules:
The merchant should not see its own offers.


Only offers in the same category as the merchant are eligible.


Choose the offer with the highest Expected Value (EVI):

 EVI = commission * conversionRate * avgOrderValue


If two offers are tied, choose the one with fewer impressions today (fair rotation).


Deliverable:
A simple implementation in Node.js/Express or Python/FastAPI (no need for DB queries — mock data is fine).
Implement the matching logic in a pure function (e.g., selectNextOffer(...)) that can be tested without HTTP.
Use mock data (in-memory) instead of a real DB.
Return a JSON response like:


{
  "offerId": "abc123",
  "advertiser": "BrandX",
  "score": 4.85
}


📌 Part 3 — Tracking Logic
Write a short explanation (no code needed) of how you would:
Record an impression reliably


Handle click tracking


Attribute a sale back to the correct merchant → advertiser pair


Avoid double-counting


Deliverable:
2–3 paragraphs max.
We want to see your reasoning, not boilerplate.
Describe the event flow (from browser / Shopify → your backend → database).
Mention how you’d handle edge cases like delayed webhooks or missing click data.


📌 Part 4 — Production Readiness (Short Answer)
Answer briefly:
“If this endpoint will serve 10M requests/day, what changes?”


“How would you protect it against abuse?”


“How would you make the system debuggable for merchants?”


(1–2 sentences each.)

🧩 What We’re Evaluating
We’re not grading beauty — we’re grading thinking:
Clarity of reasoning


Good taste in API and data structure design


Ability to simplify complexity


Correctness mindset (no double-counting, clean separation of concerns)


Startup speed (can you deliver something functional in 2–3 hours)



📤 Submission Format
A single link to a GitHub repository containing:
/schema folder → data model


/src → small working endpoint


/notes.md → tracking logic + production answers



🏁 Optional + for extra credit (not required)
Add a unit test for the matching function.
Even one test tells us about your thoroughness.
Imagine Adalore wants to add the following rules in the next 3–6 months:
Certain merchants want to exclude specific brands (never show them).


Advertisers can set a daily budget; once spent, their offers pause.


Adalore wants to run A/B tests on different matching strategies.


Question (1–2 paragraphs):
How would you evolve your current design so these rules can be added without rewriting the core matching engine?


Mention any patterns (e.g., configuration, rules engines, feature flags) you’d consider.
